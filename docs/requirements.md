# Вимоги

Стан: актуальні вимоги за ітераціями; програмні результати 01/02 і непроведені фізичні перевірки записані окремо у specs. Цей перелік не є заявою про фізичне прийняття системи.

| ID | Вимога | Етап |
|---|---|---|
| R01 | Один вхід RC-PWM насоса на ESP32-C3, вихід PWM до MD20A; DIR постійно з'єднаний із GND перемичкою на MD20A, програмного керування напрямком немає (D20). | 01–06 |
| R02 | Нативний ESP-IDF, відтворювані версії SDK/інструментів і профіль точної плати. | 01 |
| R03 | Переносима логіка без GPIO, FreeRTOS та ESP-IDF у публічних заголовках ядра. | 02 |
| R04 | Номінальне перетворення: 1000/1250/1400/1500/1800/2000 мкс → 0/25/40/50/80/100%; без автокалібрування. | 02,04 |
| R05 | Валідація перед обмеженням duty: некоректний імпульс не повинен ставати 100% через clamp. Ширина 900–2100 мкс включно (D36); для 03 також period 18000–22000 мкс включно (D41). Invalid не оновлює last-valid; capture faults і час визначено D45/D46/D51/D52. | 02,03,05 |
| R06 | PWM 1000 Гц при проміжних duty; 0% — сталий LOW, 100% — підтримуваний сталий HIGH. Фізичну дію перевірити. | 04,06 |
| R07 | За D64/D65 режим Test (за замовчуванням) при втраті свіжих valid-команд вимагає LOW після погодженого timeout; Fly утримує останню валідну команду без cutoff лише через тривалу відсутність valid. Обидва автоматично виконують нову валідну команду після відновлення, включно з високою, без ручного arming/clear. Режим задає конфігурація збірки: звичайна — Test, Fly лише явно, без runtime перемикання. D66/D69: при age≥500000мкс вимагати LOW, загальний accepted pulse_end_us→physicalLOW≤1с; технічний запас/метод визначено в Plan05, фізично не перевірено. | 05 |
| R08 | Безпечний запуск і відновлення після reset, bootloader, upload, brownout, watchdog; у05 до першого повністю валідного вимірювання поточного boot — LOW, після нього прозора трансляція за D64 без обов’язкової попередньої нульової команди. Held duty попереднього boot не відновлюється. Технічні відмови/watchdog — Q05, захист до firmware — окреме апаратне рішення. Стендовий контракт04 зберігається. | 01,04–06 |
| R09 | Захоплення, застосування режимної політики втрати сигналу й відновлення не блокуються діагностикою; невалідна активність не оновлює last-valid timestamp. Signal/capture status не може приховано підміняти Fly загальним signal-loss cutoff; технічні відмови визначаються окремо. | 03,05 |
| R10 | Локальна робота; Wi-Fi/Bluetooth вимкнені, мережевих сервісів немає. | 01–06 |
| R11 | Локальна діагностика показує сигнал, duty, стан і причину відмови, не створює додаткового джерела керування. | 03–06 |
| R12 | Програмні тести, цільова збірка й апаратне прийняття мають окремі докази. | Кожен етап |
| R13 | Другий незалежний RC-вхід для запалювання ON/OFF; інтерфейс навантаження й міжканальна політика потребують рішення. | 07, відкладено |
| R14 | Додаткові ESP32 через профілі й адаптери зі збереженням поведінки ядра. | 08, відкладено |
| R15 | Конкретна Arduino Nano через окремі таймерні/електричні адаптери й збірку. | 09, відкладено |

Система номінально 12 В, насос brushed DC. Повідомлені користувачем 15 А нормального струму, 2,5 А при 40% та робота біля 40/80% — контекст випробувань, не доведена межа startup/stall і не основа лінійної екстраполяції. Немає вимог до реверсу, автоматичного запалювання, бездротового керування чи збереженої автокалібровки.
