# Timestamp: окремий розгляд змін вимоги

Дата 2026-10-29. **Оновлення D51:** обрано напрямок оцінених GPIO ISR timestamps з окремою RMT width; hardware latch не вимагається, поріг HIGH/LOW спрощено до 100 мс із окремим бюджетом доставки fault у Plan. Наведений нижче огляд D50 збережено як історію альтернатив до цього рішення; він не скасовує актуальну [spec.md](spec.md). I2S/GDMA не потрібний для поточного напряму. Технічні першоджерела — [research.md](research.md).

## Історичний огляд до D51

| Напрямок | Що він означає | Що потрібно погодити або довести |
|---|---|---|
| Зберегти D40 на C3 | Пошук апаратного latch або hardware-sampled timestamp із доведеним clock domain, паралельно RMT RX | I2S raw PDM RX — кандидат, але його точність, epoch, DMA без втрат і deadlines не доведені; термін hardware-sampled проти edge latch потребує точного контракту. |
| Оцінений час фронтів | Висхідний GPIO ISR читає monotonic clock, RMT дає hardware width; end може обчислюватися з start+width | Це зміна D40: ISR latency входить у start/end. Потрібно оцінити асоціацію pulse/RMT, інтервальну похибку ≤10 мкс, абсолютну похибку щодо системного clock для freshness і fault ≤3/100 мс; не вважати їх пройденими без вимірювань. |
| Лише відносні hardware intervals | RMT описує duration/width/period; час отримання зберігається окремо від edge time | Змінює інтерфейс і правило last-valid: `received_at` не є `pulse_end`. Без bound доставки freshness не визначена. Не рекомендується мовчки міняти last-valid на час callback. |
| Зовнішній hardware capture або інший MCU | Зберегти hardware latch за рахунок іншого ресурсу/апаратного складу | Потрібні окремі рішення щодо scope, плати, GPIO, електрики, SDK, доказів та спільного clock. Конкретний компонент не обрано; поточний C3 profile не доводить сумісності. |

Найменша можлива зміна для software варіанта — вимагати «оцінені мітки часу фронтів у спільній монотонній шкалі з явно зазначеною максимальною похибкою», зберігши окремі hardware width, період 18–22 мс, допуски 5/10 мкс, deadlines 3/100 мс і zero-loss критерій. Проте самі 5/10 мкс не задають абсолютну похибку edge time відносно clock, яким приймається рішення про свіжість. Додаткову межу потрібно вивести з budgets і явно погодити; числа не вигадано.

Якщо зміна буде обрана, її слід записати новим рішенням, синхронізувати spec/plan/contracts, зберегти provenance measured/estimated і перевірити на максимальному навантаженні. Поточний дозвіл на дослідження не дозволяє застосувати ці зміни, почати Implement або апаратний тест.
