# Проєкт read-only діагностики flash для T008

Дата: 2026-10-28. Статус: **не виконано**; за D26/D27 користувач обрав діагностику агентом і підтвердив умови; спробу зупинено до з’єднання через недоступний порт (див. `sfdp-2026-10-28/attempt.md`). RC, MD20A та насос мають бути від'єднані. До будь-якої дії потрібне окреме явне завдання користувача та перевірка поточного живлення й порту.

## Мета й межі

Отримати SFDP header і, якщо доступна, Basic Flash Parameter Table для підтвердження заявлених flash режимів. SFDP може бути відсутня, неповна або не визначати точний part number; сама по собі вона не підтверджує стабільну роботу на частоті 40 МГц і не замінює datasheet або фізичне прийняття. За некоректного header/відповіді, помилки або непогоджених умов — зупинити; значень не вигадувати.

## Інструмент і вплив

Локально перевірено source `esptool` 4.12.0 у зафіксованому offline venv. CLI `read_flash_sfdp` використовує команду flash RDSFDP `0x5A`; `--no-stub` не завантажує flasher stub. Одна команда читає не більше 4 байтів: `run_spiflash_command` обмежує read до 32 біт. Потрібні окремі читання header, потім таблиці за реально отриманим pointer/length; тип і розташування таблиці не припускати.

«Read-only» тут означає відсутність запланованого запису flash/eFuse та відсутність erase. Це не нульовий вплив: з'єднання `--before default_reset` може скинути чип для входу в ROM; ROM/esptool налаштовують SPI і записують **volatile регістри** контролера. Код esptool 4.12.0 також може запускати послідовність виходу XMC із power-down і надсилає flash reset `0x66`/`0x99` перед командою. Не стверджувати, що reset або зміни volatile стану відсутні. Додатково не запускати `write_flash`, `erase_flash`, `write_flash_status`, eFuse burn, GPIO-команди або застосунок навантаження.

## Запропонована послідовність після окремого дозволу

1. Зафіксувати дату, виконавця, версію/hashes esptool, режим живлення та стан від'єднаних інтерфейсів. Перевірити поточну USB enumeration; попередній `/dev/cu.usbmodem1101` не вважати актуальним автоматично. Значення `SCOPA_PORT` задає оператор після перевірки; не передбачати одночасне USB VBUS і зовнішні 3,3 В як вже прийнятий режим.
2. На підтвердженому порту одноразово ідентифікувати чип у ROM, із явно дозволеним reset:

   ```sh
   /private/tmp/scopa01-replay-clean/bin/python -m esptool --chip esp32c3 --port "$SCOPA_PORT" --baud 115200 --no-stub --before default_reset --after no_reset chip_id
   ```

   Звірити MAC/unit `c3-supermini-188b0e93032c` та чип із попереднім ROM evidence. Інший unit, відсутня ідентичність чи будь-який error — stop. Не використовувати програмні GPIO-команди.
3. У тій самій ROM-сесії/стані виконати чотири окремі запити для адрес `0x0`, `0x4`, `0x8`, `0xc` (приклад першого):

   ```sh
   /private/tmp/scopa01-replay-clean/bin/python -m esptool --chip esp32c3 --port "$SCOPA_PORT" --baud 115200 --no-stub --before no_reset --after no_reset read_flash_sfdp 0x0 4
   ```

   Кожен exit code і повний stdout/stderr зберегти як окремий raw файл; повторювати з наступною адресою лише після exit 0. `no_reset` не виключає описаного вище flash reset чи volatile SPI register writes.
4. Перевірити сигнатуру `SFDP`, ревізію, кількість та типи parameter headers. Якщо headers не вміщуються в перші 16 байтів, прочитати решту короткими 4-byte запитами. Розібрати BFPT pointer/length, перед подальшим читанням перевірити коректність і обмежити довжину фактично заявленими параметрами. Зберегти всі raw байти й інтерпретацію разом із посиланням на специфікацію/первинне джерело; ніяких висновків за відсутності таблиці.
5. Зафіксувати фінальний стан порту/плати. Команди з `--after no_reset` залишають чип у ROM download mode; автоматичний перезапуск тут не передбачений. Відновлення стану — окремо погоджена дія. Оновити `board-review.md`, `research.md` і відповідні gates лише за реально отриманими даними. Результат не є H02/H03, перевіркою PWM чи прийняттям 01.

Документ підготовлений шляхом читання встановленого esptool source та CLI help; наведені команди на платі в цьому завданні не виконувалися.
