# Контракт виходу та стендової перевірки 04

Дата: 2026-10-30. Джерела: [spec](../spec.md), D57/D59/D60, [research](../research.md). Це дизайн до реалізації/вимірювань. Одиниці часу — неспадні uint64 мкс у тому самому clock domain, що capture03. Робочий дозвіл ControlCore лишається false, effective duty ядра0.

## Вхід policy та пріоритети

Portable `OutputPolicy` отримує `now_us`, незмінний `BenchConfig` для поточного boot, статус startup/capture readiness, явні capture/output/clock faults і результати попереднього застосування. GPIO/LEDC/FreeRTOS не входять до public headers. Policy не читає clock і не виконує I/O.

1. Будь-який явний fault або помилка часу/вхідного контракту → terminal Fault, permission false, запит LOW; наступні nonzero запити цього boot недійсні.
2. Справний Normal build → Disabled/LOW, незалежно від RC та reset reason. Fault має пріоритет і переводить також Normal у Fault/LOW із видимою причиною; normal ніколи не отримує bench permission.
3. Bench build → одна сесія на app boot за D59. Стан завершено/fault/evidence frozen не має переходу назад. Немає arm/clear/start command або NVS session token.
4. Початкові readiness умови не є Q05 arming: foundation ReadyDisabled, output initialization успішна, capture.start завершився та чинного capture fault немає. RC duty/valid-frame count не обирають точки чи момент запуску. При capture fault, включно з відсутнім RC/stuck, тест завершується; fault не маскується.
5. Перший owner poll фіксує t0. InitialLow триває5 000 000мкс від t0. Якщо readiness не досягнуто до t0+5с або до цього був startup/capture/output init fault — Fault/LOW, без відкладеного автоматичного запуску після retry. Foundation init retries D15 до handoff зберігаються, але факт невдалої init-спроби забороняє nonzero у цьому boot; наступний boot — нова можливість.

`request_generation` зростає при зміні запиту; fault має пріоритет над generation. Є один serialized writer policy/adapter. Перед кожною операцією, здатною встановити ненульовий вихід, включно з set/update та stop idle1 для100%, owner під коротким ISR lock знімає наявні sticky errors; fault, уже видимий у цій точці серіалізації, має пріоритет. Shared ISR lock не тримається під час SDK API. Ingress після цієї точки може з’явитися під час поточної операції: owner повторно перевіряє sticky flags одразу після API, застосовує fault/LOW до будь-якого наступного nonzero API, включно з stop idle1, зокрема між set та update. Не обіцяється фізично атомарна пара ISR-ingress/LEDC write; budget починається від застосованого owner fault, а source-to-LOW має окремий прямий критерій. Повторне застосування тієї самої generation не змінює апаратний стан і не створює replay. uint64 addition/subtraction та time regression перевіряються до обчислень; помилка → ClockError/LOW. Прямий percent>100 відхиляється як InvalidRequest/LOW, без clamp. Capture invalid зберігає семантику03 і сам не є output fault.

## Скінченний сценарій і build identity

| Варіант | Початковий LOW | Кожна з6 точок | Deadline кінцевого LOW API від t0 |
|---|---|---|---|
| normal | Постійно | Немає | Весь boot LOW |
| waveform | 5с | 10с | 65с + бюджет LOW API2мс |
| stress | 5с | 100с | 605с + бюджет LOW API2мс |
| accuracy | Як waveform | Як waveform до evidence freeze | Раніше65с: LOW перед зупинкою capture/export |

Послідовність рівно0/25/40/50/80/100%, далі LOW; додаткових пауз між кроками немає. Крок0 теж має повну тривалість. Deadlines абсолютні від t0, не накопичують drift від часу poll. Плановий перехід виконується лише на першому poll на/після deadline. Lateness>1000мкс → DeadlineLate/Fault/LOW, а не видача пропущених duty заднім числом. При одночасному fault та переході виграє LOW. Після завершення — LOW необмежено, без loop.

Технічні build inputs: майбутній target-only `--pump04-bench waveform|stress|accuracy`; без flag — normal. Kconfig `BRIDGE_PUMP04_BENCH` default n, scenario choice і trace step є build-time constants; немає console чи runtime configuration. Відомості про scenario/config hash входять до build manifest. Комбінації `--pump04-bench` із `--rc03-bench` відхиляються: кожен04 fragment сам визначає потрібні stress/trace03 settings, без прихованого merge режимів.

waveform: trace off, diagnostics звичайні. stress: trace off, чинне padding384B/100мс. accuracy: diagnostics stress on, trace03 on; явний аргумент `--pump04-trace-step 0..5` обов’язковий для accuracy, без мовчазного default, і допустимий лише тут і визначає тільки початок збору доказів, а не duty-послідовність. Наступні вікна — окремі boot, не команда.

Reset будь-якої причини знову проходить startup/InitialLow і може виконати нову сесію; старий крок не поновлюється. Власний automatic reset не додається. Відкриття reader не запускає тест; якщо host реально спричинив reset, працює правило нового boot. Standalone bench image не є штатною прошивкою для насоса.

## Апаратний adapter

Єдиний `EspPumpOutput` реалізує foundation OutputPort LOW та04 output requests. app володіє ним лише до handoff; capture/control owner — після handoff. Немає другого GPIO0 writer. ISR/diagnostics не керують виходом.

- GPIO0, LEDC_LOW_SPEED_MODE, timer0/channel0, LEDC_USE_APB_CLK80МГц, resolution13bit, hpoint0, inversionfalse, no fade, no sleep. Інші LEDC clients не використовують timer/channel; clock/PM/sleep03 не змінюються.
- Нормальний image залишає GPIO LOW і не запускає nonzero generator; bench timer/channel конфігуруються з duty0 після попереднього GPIO LOW. Перевірити всі top-level return/status. Частковий setup не означає Ready.
- 1..99%: count=(percent×8192+50)/100, checked set_duty_with_hpoint→update_duty.25→2048;40→3277;50→4096;80→6554. Не використовувати fade, ledc_set_duty_and_update, duty8192 або довільний hpoint.
- 0%: checked ledc_stop(...,0);100%: checked ledc_stop(...,1). Timer залишається зарезервованим; повернення до PWM через set/update знову вмикає output. Сталий HIGH не має періодичних LOW pulses.
- На будь-якій API error спершу policy terminal fault/permissionfalse та інвалідація generation. Спробувати stop0, навіть після часткового set/update. За невдалого stop або відсутнього channel — GPIO fallback: checked set_level0, потім checked set_directionOUTPUT, що повертає matrix до простого GPIO. Записати status кожної операції; failure не приховується наступним success. Після fallback жодний stale update не дозволений у цьому boot.
- Нездатність установити LOW → `LowUnconfirmed`, failed acceptance; не заявляти physical cutoff. У normal/terminal стані немає nonzero retry. Cleanup timer pause/deconfigure виконується лише після LOW/reroute; API cleanup failure фіксується. GPIO reset_pin не використовується як LOW cleanup.
- apply_low після handoff не обходить adapter і не міняє GPIO direction під активним PWM. Startup supervisor після ReadyDisabled не перехоплює owner. App start/retry має явний одноразовий handoff, задачі не видаляються, поки володіють виходом.

API-return/частотний readback/стан pin matrix — програмні факти; фізичний LOW/HIGH доводить тільки прилад. MD20A LOW — brake, не power isolation; DIR тільки апаратна GND перемичка.

Це вимоги до майбутньої реалізації, не вже досягнуті RT гарантії. Непередбачена зупинка owner може порушити deadline; при відновленні — негайний LOW, фактичний lateness і failed test. Watchdog05 та незалежне силове відключення06 не замінюються цими числами. Не розширювати допустимі capture бюджети03, щоб умістити новий output path.

## Фізичні допуски M04

1. Для кожного стабільного періоду проміжних duty: |f−1000Гц|≤1Гц та |d−номінал|≤0,1 відсоткового пункту. U_f≤0,1Гц, U_d≤0,02п.п. документуються окремо. Пряме порівняння E з допуском, без averaging, округлення, offset/drift adjustment для pass. Ці output U-вимоги не змінюють D54 для capture.
2. Основні stable windows: у waveform від+1с до+9с кожного10с plateau; у stress від+1с до+99с кожного100с plateau. Кожен complete period у вікні перевіряється; endpoints спостерігаються протягом повного plateau. Перший/останній1с не ігноруються: окремий transition analysis: API deadline2мс у MCU clock, фізичні відстані між ідентифікованими сусідніми переходами мають відповідати кратним plateau duration з E≤0,001×T_nom+2000мкс та окремою U_T≤0,0001×T_nom+100мкс (T_nom у мкс); для10с це12мс/1,1мс, для100с102мс/10,1мс, після settling поза stable window не допускається подальших спотворень.
3. Static LOW на GPIO0 та PWM driver input: виміряне V_low+U_V≤0,8В. HIGH: V_high−U_V≥2,4В та V_high+U_V≤3,6В. U_V≤0,05В, відносно відповідного GND. Це обрані інженерні acceptance limits до тесту, не виміряні рівні; для іншої фактичної ревізії драйвера її специфікація перевіряється до використання. Ground shift/overshoot не повинні порушувати межі компонентів.
4. Digital acquisition sampling≤0,1мкс (≥10MS/s); для analog voltage/transients — bandwidth≥10МГц та sampling≥20MS/s або інша попередньо доведена еквівалентна методика. Калібровані пороги/часова база/навантаження probe та glitch detect мають доводити виявлення протилежного рівня тривалістю≥1мкс. Крок sampling сам не є повним U. Невідомий U/insufficient bandwidth/прогалини запису → blocked, не pass. Поведінка коротше1мкс не вважається доведеною.
5. Startup waveform до першої навмисної nonzero команди: прилад захоплює подію з pretrigger≥10мс, повну boot/initial LOW область та≥10мс після першого переходу. Reset/bootloader/upload аналогічно, з ідентифікованими boundaries; у bootloader безстроковий LOW перевіряється в заданому операторському інтервалі≥10с. Для кожного cold-start/reset/bootloader/upload мінімум5 повторів у disconnected-driver і powered-driver умовах. Фактичний канал board і driver input записані окремо або одночасно, з provenance.
6. Перевірка частот/duty не означає physical action MA/MB або motor direction. MD20A ревізія/ground/перемичка/кнопки — окремий запис без мотора; powered-driver test лише після Q06 interface gate, неперевірене живлення не вмикається автоматично.

## Bounded вимірювальні записи та зіставлення часу

Тільки в окремих04 bench images дозволений `OutputEvidence`: до64 records×40B + header≤128B, максимум2688B; без heap/overwrite/I/O в owner. Record: event_seq uint32, kind uint8, requested_percent uint8, apply_state uint8, reason_bits uint8, before_us uint64, after_us uint64, deadline_or_fault_us uint64, sdk_status int32; native record≤40B із alignment, canonical serialization36B без padding. Header: build/scenario/boot identity, count, frozen, overflow, bounds. Події — початок/кінці API-змін та fault/terminal, не кожен PWM edge. Повний buffer→EvidenceOverflow/Fault/LOW, неповний/overflow архів не дає timing pass. Переповнення логується sticky прапорцем у зарезервованому header; owner зупиняє append, а пріоритетний LOW/fallback виконує незалежно від вільного місця. Логування цих terminal операцій best-effort до capacity, без повторного виклику overflow-handler або рекурсії; втрачений raw record не підміняється success, архів incomplete/overflow є failed evidence. Вимога status кожної операції стосується повного неoverflow архіву; сам failure path не очікує recorder.

Кожна змінена команда має before/after API bracket та raw status кожної операції. API/fault/deadline budgets перевіряються тільки в одному MCU-clock domain. Фізична форма, періоди/plateau intervals і прямий GPIO3-stuck→GPIO0-LOW112мс перевіряються аналізатором. Для startup без попередньої зміниGPIO3 фізичний початок спостереження/fixture event фіксується приладом, не підміняється USB-текстом.

Не виводити невідомий clock offset із самих output transitions та припущеної затримки API: спільний додатковий physical delay усіх переходів може сховатися в offset. Абсолютна owner-fault→physical LOW≤2мс не заявляється й не є acceptance claim04 без незалежного cross-domain anchor, якого поточний профіль не надає. Offline tool перевіряє MCU API та фізичні метрики окремо; спроба попросити cross-domain pass без незалежного calibration provenance дає blocked. Негативний fixture зі спільним shift>2мс не повинен давати такий pass. Runtime API record не підміняє виміряний LOW.
Після terminal LOW output archive передається sole USB writer, ≤384B/frame,≥100 мс, drain/zero-wait. У stress за D62 цей export додатково чекає freeze CaptureWindowEvidence після t0+606 с; сам Output Complete на 605 с не відкриває export phase. Marker `rc04-out`; HEADER, indexed RECORDs, END(count/FNV-1a64 identity за схемою data-model.md). Фіксований архів може повторюватися після reconnect лише в explicit evidence export phase; активна production/bench diagnostics історії не має. Capture та його звичайна діагностика можуть працювати далі, але export замінює snapshot у цьому слоті, не додає другого writer/record. Кожний archive frame містить поточний fault summary; пізніший fault лишається sticky/latest і не стирається архівом. Mixed/incomplete cycles не evidence. Normal image не має OutputEvidence/архіву.

Accuracy03 D55: збір128 candidates починається після+1с обраного trace_step (0..5). До цього capture працює, але collector не заповнюється; це тільки зміна bench instrumentation, не validation/last-valid. На freeze output permission знімається й checked LOW застосовується ДО навмисної зупинки capture. Якщо будь-який LOW API повернув error, сесія переходить Fault, навіть за успішного fallback; такий accuracy run не pass. Якщо LOW не встановлено навіть fallback, LowUnconfirmed має пріоритет: нормальний evidence-freeze/stop не виконується, capture/diagnostics продовжуються за своїм lifecycle, evidence лишається failed. Це не забороняє cleanup capture з його власної причини. За успішного LOW можна завершити stopped/export фазу, зберігаючи fault і неприйнятність вікна, якщо він уже є. Далі чинний rc03-trace exporter, а потім rc04-out, одним writer/слотом. Вікно per-pulse E5/10мкс/U≤1мкс незмінне, records не відбираються. Такий образ не є доказом повної65с послідовності/600с loss: ці критерії мають власні waveform/stress runs. Якщо trace completion супроводжується fault — fault має пріоритет і вікно не приймається.

## Діагностичний запис rc04

Нормальна latest-only semantics03 збережена:≤10 записів/с,spacing≥100000мкс,transport≤384B,TX512/RX128,one committed/in-flight record, zero-wait/drop/counters. Всі числові поля нового `rc04` — hexadecimal без0x; parser03 не використовується мовчки. `rc03-trace` grammar незмінна.

Форма record: newline, `rc04 q=... id=... sid=... w=... s=... e=... p=... v=... c=... d=... o=0 a=0 f=... n=... k=... m=... t=... b=... x=... z=...`, newline. q/id/sid/start/end/timing values64bit; w/p32bit; v/c one hex digit; d≤64hex; f≤7ff; n шість32bit counters; k чотири32bit diagnostic counters та64bit bytes; m три64bit maxima; t threshold/reported64bit; b startup phase/attempts≤5/error/low-status; x saturation bool. z=mode,phase,requested_percent,bench_permission,apply_state,output_reason_bits (1/1/2/1/1/2 hex digits).

Нові z поля ніколи не підміняють o/a: ті залишають effective core0/workpermissionfalse; requested output окремий. API-applied state не є measured voltage. За повних64/32bit величин і допустимих enum/mask меж максимум383B із framing, capacity385 включно з NUL. Потрібні boundary test/compile check при реалізації; якщо payload завеликий — відмовити форматуванню й підрахувати drop, не приховати поля/обрізати record. Stress padding до384B дозволене в одному frame за чинним03 правилом.

Offline physical input: CSV `time_ns,channel,level`, integer ns, channel gpio0/gpio3, level0/1, monotonic і alternating edges на кожному каналі з однією analyzer timebase. GPIO0 — PWM; GPIO3 — джерело112мс fault check. Прогалини/невідомі boundaries та відсутнійGPIO3 блокують відповідну метрику. Модель03normalized pulse_start_ns/pulse_end_ns для capture comparator не змінюється. Physical600с source/counter window має явне погоджене зіставлення pulse boundaries/boot і actual counter checkpoints; невстановлена відповідність не замінюється припущенням30000 або best-fit.

## Уточнення якості вимог перед Tasks

Для112мс physical case до T0 має бути підтверджений потрібний ненульовий plateau без попереднього terminal fault. T0 — остання спостережена змінаGPIO3, яка починає обраний stuck episode. T_cut — max(T0, початок останньої безперервної LOW-ділянкиGPIO0), яка зберігається протягом повної terminal області запису, щонайменше10с після T_cut за наявним no-repeat guard P2/P5. Звичайна LOW-частина PWM не є cutoff. Будь-який наступний HIGH≥1мкс у цій області порушує terminalLOW/no-repeat. Прогалини запису/невідомий initial state/відсутній попередній active plateau блокують цей case; latency=T_cut−T0 має бути≤112мс. Напругова LOW-придатність приймається окремо за M04, не припускається з digital0.

CSV містить тільки edges; metadata version1 обов’язково має acquisition_start_ns, acquisition_end_ns, initial_levels для кожного потрібного каналу, observed_windows (інтервали доведеного безперервного спостереження), gap/overflow indicators та raw provenance. Час/рівень першого edge не замінює initial_levels. Порожній список edges може підтверджувати static endpoint лише за відомого початкового рівня, достатньої тривалості та gapless запису всього потрібного plateau; сам порожній CSV не є evidence. Межі всіх GPIO каналів мають одну analyzer timebase. Дані для analog voltage зберігаються окремо.

Нормативні wire enum-коди й record/header status semantics визначено у data-model.md; ці коди стабільні незалежно від внутрішніх C++ enum ordinals. Невідомий код/відсутнє обов’язкове поле — malformed/blocked input, не підстановка default.

## Stress window evidence — D61/D62 / CHK023–024-A, U1-A

CaptureWindowEvidence≤512B незалежний від USB. Облік починає спостерігати provenance до start=t0+5 с; фіксоване вікно тривалістю601 MCU-секунда [start,end), end=t0+606 с за D62. Pre-window sample, оброблений після start, не додається; належний sample, оброблений після end, додається до closing summary. На start/end owner зберігає actual-time global checkpoints без reset live counters. Окремі window-local counts/maxima та first/last seq/epoch/end доводять саме вікно; cumulative delta global snapshots цього не замінює. Невідомий end/epoch, неповний candidate, saturation/drop/reorder/duplicate або fault без однозначного віднесення до bounds роблять evidence incomplete/failed; їх не відкидають для pass. Після end+6 мс короткий shared ingress lock фіксує producer watermark/epoch closure; owner поза lock drain-ить і асоціює всі належні records до цього watermark. Нові post-window epochs продовжують capture та не перешкоджають закриттю старого вікна.

Якщо callback/обробка/barrier не вкладаються або асоціацію довести не можна, owner фіксує frozen incomplete/failed evidence, не очікує нескінченно й не ставить pass за самим timer. Пізня належна подія після freeze піднімає окремий sticky postfreeze_invalid; immutable counts/digest не переписуються. Звичайні події після end у підсумок не входять.

Протягом 601 MCU-секунди і closing export немає. Live sticky capture/output/postfreeze_invalid flags є в кожному frame. Capture продовжується; stress на відміну від accuracy не переходить у capture-stopped. Відсутній reader не змінює collector/closure, reconnect не перезапускає test. RAM summary зберігається до нового boot, повтор export того самого frozen циклу не є новим вимірюванням. Формат/розміри та malformed/partial/mixed cycles потребують meaningful formatter/parser fixtures при реалізації.

Ця асоціація не калібрує output API→physical clock offset і не додає cross-domain latency claim.


### Фізична тривалість D62

601 MCU-секунда — номінальний запас збору, а не доказ 600 фізичних секунд. До run методика задає правила однозначного зіставлення first/last належних falling із raw analyzer pulse indices та duration_uncertainty_ns із calibration/timebase provenance; фактичні pulse indices підтверджуються за raw record після run. Консервативний достатній доказ: T_obs — фізичний інтервал між цими first/last falling всередині RAM-вікна; T_lower=T_obs−U_duration. Для pass T_lower≥600000000000 нс (600 с), gapless спостереження всього інтервалу та узгоджені source/window counts/order без втрат. Короткі поля до first/після last не використовуються для штучного збільшення покриття. Якщо число належних samples<2, boundary association/gaplessness або U невідомі — blocked; за придатного повного методу T_lower<600 с — fail недостатньої тривалості. Сам 601000000 мкс, номінальні 50 Гц/30000 або offset через PWM transitions не дають pass.

Це lower-bound правило тільки для мінімального часу покриття. Воно не змінює прямі E/U правила частоти/duty M04 чи width/interval D54. Не допускаються усереднення, backdating, продовження 601 MCU-секундного collector під час run, нова runtime-команда або автоматичний повтор, щоб добрати тривалість. Якщо запасу не вистачило, run failed/blocked за відповідною причиною; подальша зміна дизайну потребує явного рішення. Output plateau залишаються 100 MCU-секунд, їх physical interval допуски M04 перевіряються окремо.
