# Промпти Spec Kit

Це вхідні матеріали, а не готові специфікації. Загальний [roadmap](../docs/roadmap.md) визначає залежності. Кожна з дев'яти ітерацій має `specify.md`, `plan.md` і `manual-step.md`.

Після програмних ітерацій 01–03 наступний етап — 04. Промпти 04–09 узгоджено з D10–D56 та чинними контрактами; перед використанням обов'язково читати [спільний контекст](current-baseline.md). Промпти 01–03 і [constitution-prompt.md](constitution-prompt.md) збережено як початкові входи вже проведених фаз; вони не є актуальним завданням повторно обирати SDK, GPIO чи правила валідації. Повертатися до цих фаз лише за окремим запитом із чинними рішеннями.

Програмна реалізація 01–03 не дорівнює фізичному прийняттю: 02 має власні виконані програмні критерії за D38; фізичні перевірки 01/03 відкриті. Актуальні докази — у `specs/01-foundation/verification/acceptance.md`, `specs/02-control-core/verification/acceptance.md` та `specs/03-rc-capture/verification/acceptance.md`. Старі статусні абзаци architecture/roadmap не замінюють цих записів. Залежні апаратні дії потребують відповідних gates; підготовка spec/plan не оголошує їх пройденими.

## Запуск у Codex

Установлений CLI 0.12.17 створює skills у `.agents/skills/`. Для Codex фактичні виклики — `$speckit-constitution`, `$speckit-specify`, `$speckit-clarify`, `$speckit-plan`, `$speckit-tasks`, `$speckit-analyze`, `$speckit-implement`. Назви `speckit.constitution/specify/plan` у початковому завданні відповідають цим skills. Якщо вони ще не відображаються, відкрити новий сеанс Codex у цьому каталозі.

1. Прочитати [конституцію v1.0.0](../.specify/memory/constitution.md), ухвалену 2026-10-28. [constitution-prompt.md](constitution-prompt.md) залишається входом первинного ухвалення; повторно запускати constitution лише за окремим завданням на її зміну. Ухвалення не запускає наступні фази й не завершує ітерацію 01.
2. Для наступної ітерації передати `$speckit-specify` її промпт. Наприклад: «$speckit-specify прочитай і виконай промпт у speckit-iteration/04-pump-output/specify.md разом із speckit-iteration/current-baseline.md». Під час Specify створити/перемкнути гілку `04-pump-output` за `AGENTS.md`/D10, зберігши роботу користувача.
3. Прочитати отриману специфікацію, закрити блокувальні питання; за потреби окремо викликати `$speckit-clarify`.
4. Передати `$speckit-plan` вміст `04-pump-output/plan.md` разом зі спільним контекстом. Це генерує план, а не реалізацію. Інші етапи використовують власні промпти й каталоги.
5. Після перевірки плану окремо запускати Tasks, за потреби Analyze, потім Implement за відповідним завданням. Фізичні перевірки проводити за `manual-step.md` та прийнятим планом.
6. Перевіряти залежності за межами конкретної фази: невиконані фізичні перевірки записувати як gates, не видаючи їх за pass. D38/D48 не скасовують обов'язкових фізичних критеріїв 01/03 або вимог до роботи з насосом у 06. 07–09 залишаються відкладеними до окремого запиту.

## Вибір feature

Промпти явно задають `SPECIFY_FEATURE_DIRECTORY=specs/<ідентифікатор>`. Установлений workflow підтримує явний каталог; автонумератор за замовчуванням створює тризначні імена, тому на нього тут не покладатися. Для ручного виклику скриптів з кореня, **після створення spec**, приклад:

```sh
SPECIFY_FEATURE_DIRECTORY=specs/04-pump-output bash .specify/scripts/bash/setup-plan.sh --json
```

Сам цей скрипт лише готує файл із шаблону, він не замінює `$speckit-plan`. Не запускати його під час редагування промптів. Перед кожною фазою перевіряти обраний каталог; `.specify/feature.json` може зберігати попередню ітерацію й не є джерелом правильного вибору. Це локальний стан, він ігнорується Git. Ім'я Git-гілки не визначає шлях артефактів. Git extension не встановлено; feature-гілка готується під час Specify за прямим правилом `AGENTS.md`/D10, без автоматичних комітів чи push.

Для підготовки feature-гілки перенесено helper `create-new-feature.sh`
та `common.sh` із `Lora_clone`, з базою `main`, яку можна змінити через
`SPECIFY_BASE_BRANCH`. Див. [передумови й команди](../scripts/README.md).
Наявну специфікацію відновлювати з `--allow-existing-branch`; копіювання helper
не вмикає автоматичних Git-hooks. У межах Specify поточне правило вже дозволяє
підготовку відповідної гілки; інші фази її самі не перемикають. D10 є прямим
винятком до старої загальної заборони гілок у принципі V конституції, а не дозволом
commit/push або апаратних дій. Цю розбіжність явно відображено в спільному контексті;
зміна промптів сама не ухвалює поправку до конституції. Якщо helper блокує
перемикання через незбережені зміни, не обходити захист через stash/reset/clean/commit.

Правила проєкту й конституція мають пріоритет над загальними defaults skills. Зміни поведінки потребують змістовних тестів; обов'язкового test-first циклу немає. Не підставляти відповіді на блокувальні Q01–Q09 через ліміт уточнень. Не прошивати плату й не керувати навантаженням без відповідного явного завдання.

## Результати

`specs/<ітерація>/spec.md`, `plan.md` та потрібні research/contracts/quickstart/tasks створюються відповідними командами. Докази після реалізації — у `verification/` цього feature. Саме створення документів не є завершенням ітерації, збіркою чи фізичним прийняттям.


## Рішення05 від2026-11-06

D63–D65: вхід — вихід Matek H743-Wing/ArduPilot; конвертор валідовує й транслює команду, без логіки двигуна. Окремі конфігурації збірки Test(default)/Fly: Test→LOW після погодженого timeout; Fly→hold останньої valid без signal-loss cutoff; обидва автоматично виконують нову valid, включно з високою, без попереднього нуля/додаткового arming/ручного clear. До першої valid поточного boot — LOW. Числовий Test timeout і технічні failure/watchdog деталі ще Q05. Політика поки документальна; firmware04 і фізичні gates не змінені. Старий принципII конституції потребує формальної синхронізації до реалізації05, без автоматичного виклику наступної фази. Чинні деталі — [current-baseline.md](current-baseline.md) та [рішення](../docs/decisions.md).
