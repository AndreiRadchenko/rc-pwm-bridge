# Промпти Spec Kit

Це вхідні матеріали, а не готові специфікації. Загальний [roadmap](../docs/roadmap.md) визначає залежності. Кожна з дев'яти ітерацій має `specify.md`, `plan.md` і `manual-step.md`.

## Запуск у Codex

Установлений CLI 0.12.17 створює skills у `.agents/skills/`. Для Codex фактичні виклики — `$speckit-constitution`, `$speckit-specify`, `$speckit-clarify`, `$speckit-plan`, `$speckit-tasks`, `$speckit-analyze`, `$speckit-implement`. Назви `speckit.constitution/specify/plan` у початковому завданні відповідають цим skills. Якщо вони ще не відображаються, відкрити новий сеанс Codex у цьому каталозі.

1. Прочитати [конституцію v1.0.0](../.specify/memory/constitution.md), ухвалену 2026-10-28. [constitution-prompt.md](constitution-prompt.md) залишається входом первинного ухвалення; повторно запускати constitution лише за окремим завданням на її зміну. Ухвалення не запускає наступні фази й не завершує ітерацію 01.
2. Передати `$speckit-specify` вміст `01-foundation/specify.md`. Наприклад: «$speckit-specify прочитай і виконай промпт у speckit-iteration/01-foundation/specify.md».
3. Прочитати отриману специфікацію, закрити блокувальні питання; за потреби окремо викликати `$speckit-clarify`.
4. Передати `$speckit-plan` вміст `01-foundation/plan.md`. Це генерує план, а не реалізацію.
5. Після перевірки плану окремо запускати Tasks, за потреби Analyze, потім Implement за відповідним завданням. Фізичні перевірки проводити за `manual-step.md` та прийнятим планом.
6. Лише після виконання й прийняття залежностей переходити до наступного етапу. 07–09 залишаються відкладеними до окремого запиту.

## Вибір feature

Промпти явно задають `SPECIFY_FEATURE_DIRECTORY=specs/<ідентифікатор>`. Установлений workflow підтримує явний каталог; автонумератор за замовчуванням створює тризначні імена, тому на нього тут не покладатися. Для ручного виклику скриптів з кореня, **після створення spec**, приклад:

```sh
SPECIFY_FEATURE_DIRECTORY=specs/01-foundation bash .specify/scripts/bash/setup-plan.sh --json
```

Сам цей скрипт лише готує файл із шаблону, він не замінює `$speckit-plan`. Не запускати його під час первинного scaffold. Перед кожною фазою перевіряти обраний каталог; `.specify/feature.json` може зберігати попередню ітерацію й не є джерелом правильного вибору. Це локальний стан, він ігнорується Git. Ім'я Git-гілки не визначає шлях артефактів. Git extension не встановлено; автоматичних комітів/гілок немає.

Для окремо запитаного створення feature-гілки перенесено helper `create-new-feature.sh`
та `common.sh` із `Lora_clone`, з базою `main`, яку можна змінити через
`SPECIFY_BASE_BRANCH`. Див. [передумови й команди](../scripts/README.md).
Наявну специфікацію відновлювати з `--allow-existing-branch`; копіювання helper
не вмикає автоматичних Git-hooks і не скасовує вимогу явного завдання.

Правила проєкту й конституція мають пріоритет над загальними defaults skills. Зміни поведінки потребують змістовних тестів; обов'язкового test-first циклу немає. Не підставляти відповіді на блокувальні Q01–Q09 через ліміт уточнень. Не прошивати плату й не керувати навантаженням без відповідного явного завдання.

## Результати

`specs/<ітерація>/spec.md`, `plan.md` та потрібні research/contracts/quickstart/tasks створюються відповідними командами. Докази після реалізації — у `verification/` цього feature. Саме створення документів не є завершенням ітерації, збіркою чи фізичним прийняттям.
